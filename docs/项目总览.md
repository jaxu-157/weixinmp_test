# Vision-Triage 项目总览

> 读者定位：想快速搞懂本项目全貌的人（README 级总览）。
> 所有数字均出自 `docs/_FACTS_verified.md`（唯一数字真值源）。该清单没有的数字一律标"未测/不适用"，绝不臆造。

---

## 1. 一句话定位

**Vision-Triage 是一个面向微信小程序的"故障检测 + 三轴分诊 + 根因定位"诊断引擎**：以视觉感知为主轴，融合功能与性能信号，在不依赖人工标注的前提下，对真实第三方小程序注入的故障做检测、分类（功能/性能/视觉），并把视觉异常定位到源文件、把数据字段异常定位到源码行。

---

## 2. 解决什么问题

小程序质量保障里，传统手段各有盲区：

- **崩溃监控（crash-only）只抓硬崩溃**，对"图糊了/图没了/布局错位/数据字段错了"这类"页面还在但内容坏了"的软故障无能为力。
- **人工巡检不可规模化**，且无法给出"这是哪一类问题、坏在哪个文件/哪一行"。
- **纯 LLM 视觉判断有系统性偏见**（见第 6 节 Qwen 负结果），不可直接当检测器。

Vision-Triage 的目标是：用**确定性、零 LLM 调用**的方式，做到

1. **检测**：发现页面级软故障，且对健康页几乎不误报（多条证据线健康假阳 = 0%）。
2. **分诊**：把异常归到三轴——功能（Afunc）/ 性能（Aperf）/ 视觉（Avisual）。
3. **根因定位**：视觉异常 → 源 `.vue` 文件；数据字段异常 → 源码行。

并以**真实第三方开源 app + 源码变异基准 + bootstrap 95% CI** 给出可复现、带置信区间的数字，而不是单 demo 上的硬编码结论。

## 3. 系统架构：一个引擎 + 两条取信号路径

> 核对代码：这是 **一个诊断引擎 + 两条取信号路径**，不是两套系统。

### 3.1 一个诊断引擎（三轴分诊）

- 诊断引擎代码：`fault_bench/vt_diagnose.py`、`diagnosis/diagnose/triage.py`
- 三轴 = **视觉 / 功能 / 性能**（对应中期就提出的三重断言概念 Afunc / Aperf / Avisual）。

### 3.2 两条取信号路径

| 路径 | 入口代码 | 载体 | 取到的信号 | 喂养证据线 |
|---|---|---|---|---|
| ① H5 无头截图（不用 devtools） | `fault_bench/bench/renderer.py` + `fault_bench/bench/run_campaign.py`（Playwright 无头渲染 uni-app 编译出的 H5） | 小兔鲜儿 uni-app（开源） | 分块 SSIM（8×3，阈值 0.85）+ 整图 SSIM + DOM 几何 | **A / B / D 线** |
| ② devtools 真机（minium 零侵入只读） | `auto_test/v2_modules/devtools_probe.py`（minium connect，只读不注入） | youzouzou 原生 WXML 小程序 | `page.data` + `wx.getPerformance` + 元素真几何 `scrollWidth` | **C 线** |

### 3.3 两路对应哪些证据线、各自盲区与互补

- **路径①（H5）**：全自动、可大样本（A 线 20 故障 / 5 健康一次跑完），但有**数据盲区与性能盲区**——H5 prod 编译掉 `{{ }}`，运行时拿不到字段名；零侵入下检测不到主线程阻塞（见第 6 节 R1）。
- **路径②（devtools）**：靠 `page.data` 补数据盲区、靠真几何补几何盲区、靠 `wx.getPerformance` 接真实性能，但**样本小、需人工打开开发者工具**。
- **互补**：H5 负责"广"（大样本、跨页），devtools 负责"深"（结构化数据 / 真几何 / 真性能）。C 线正是用 devtools 抓到了 H5 截图漏掉的数据/几何故障。

## 5. 根因定位（本轮新增，确定性、无 LLM）

| 能力 | 产物文件 | 结果 |
|---|---|---|
| 视觉 → 源文件（单点 hash，旧） | localization_v2 | 4/10 = 40% |
| 视觉 → 源文件（bbox 面积排序，新） | localization_v2 | **文件级 8/10 = 80%；组件级 9/10 = 90%** |
| 功能 字段 → 源码行（给定坏字段名） | field_line | **5/5 = 100%** exact |
| 功能 page.data 坏字段 → 源码行（端到端闭环，离线合成数据） | datafield_loop | **4/4 = 100%** |

### 5.1 视觉定位链路

分块 SSIM 最低 tile 集 → 与所有元素 `getBoundingClientRect` 求交叠面积 → 面积最大且非根容器的元素 → `data-v` hash → `.vue` 源文件。

### 5.2 两种关键修法

- **修法①：用 `data-v` hash 而非 class**。每个 `.vue` 的 `data-v` hash 唯一、不撞车；而 class 会被 uni 框架的 wrapper 类污染。hash → 文件 6/6 全对。
- **修法②：用 bbox 面积排序替代单点 `elementsFromPoint`**。单点会命中相邻元素或大容器；改成"与坏 tile 交叠面积最大"后，文件级定位从 **4/10 提升到 8/10**。
- 视觉定位三步迭代：0/10（class）→ 4/10（hash + 单点）→ 8/10（hash + bbox）。

### 5.3 实测落点（FACTS 逐项）

- 字段 → 行 5/5：XtxGuess `item.name`→L64 / `item.price`→L67；HotPanel `item.title`→L15 / `item.alt`→L16；CategoryPanel `item.name`→L20。
- page.data 闭环 4/4：`guessList[0].price`→L67、`name`→L64、HotPanel `alt`→L16、CategoryPanel `name`→L20（由合成 page.data 驱动；真机换成 minium page.data 即端到端，**真机验证待做**）。

### 5.4 诚实的平台不对称

字段名运行时恢复在 minium **原生路径直接可达**（page.data 结构化命名坏字段，`devtools_probe.collect_data` 新增 `suspicious_fields` / `broken_field_paths`）；但 H5 prod 编译掉 `{{ }}`、Vue per-node 实例不可达，**H5 路径的字段名运行时恢复仍是缺口**。

## 6. 诚实负结果（方法学严谨的体现，全部实测）

- **R1 性能维 H5 零侵入 = 负结果**：注入 onLoad 阻塞 1.4s，墙钟 time-to-content delta 同一注入两次 1359ms vs 172ms（方差 > 注入量，不可复现）；headless Long Task API 对 1.4s 阻塞只报约 80ms；FCP 不变。→ **H5 零侵入检测不到主线程阻塞，性能维是盲区。**
- **R2 残留 FPR 根因 = 跨构建基线（非轮播抖动）**：同会话/同构建 FPR 0%；旧 build 的 baseline vs 新 build 渲染整体 SSIM 约 0.49 → 跨构建混用产物全假阳。**已修（同构建取样）。**
- **Qwen-VL 单图 = 系统性偏见**：对带纹理的占位图，每张（含健康基线）都判 `has_missing_image=True` → 100% 检出是假象、健康页 100% 误报；差分融合（图+基线+代码）虽消除偏见但太保守（recall 30%）。→ **Qwen 当前不可用作视觉检测通道；正确用法是"已定位区域的解释器"而非"检测器"。**
- 性能定位若要做：CDP Profiler（Playwright `newCDPSession` 可驱动）+ source-map 可给函数/行级，确定性；但 H5 检测是前提（盲区卡住），原生微信深 CPU profiler 是 GUI-only（minium 拿不到）。

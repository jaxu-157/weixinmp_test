# Vision-Triage v2 结题报告

> 课程项目结题文档 · 2026-05

## 摘要

本课程项目针对微信小程序中"页面卡顿、白屏、模糊、错位、显示旧数据"等表象性故障难以快速归因的问题，设计并实现了 **Vision-Triage**——一套基于功能、性能、视觉三模态证据融合的小程序故障分诊系统。

在第一阶段原型完成后（uni-app Demo + FastAPI 诊断后端 + 14 用例矩阵化测试），团队收到外部评审反馈：现有方案在 ASE/FSE 级 prior work（Owl Eyes、Trident、Uber Chaos、WeDetector 等）面前 contribution 偏弱。本项目第二阶段（v2）针对该评审意见进行了系统性改造，分**五个**阶段重新组织 contribution：

1. **可学习的维度化根因分诊（Phase 1）**——把原先的手写真值表替换为浅决策树，准确率从 74% 提升到 91%（macro-F1: 0.72 → 0.91）
2. **Rule→MLLM 级联视觉 Oracle（Phase 2）**——规则法做廉价 pre-filter，置信度低时升级到多尺度启发式或 MLLM，仅 57% 样本需要升级
3. **可复现的故障基准（Phase 3）**——构建 350 样本的特征级 benchmark，覆盖 14 个 (页面, profile) 场景 × 25 强度档位，含 28% 的边界样本
4. **可嵌入任意小程序的 SDK（Phase 4）**——抽出 `vision-triage-sdk` npm 包，在 3 个独立样例小程序上验证，平均集成成本 **13.85%** LOC
5. **v2 Driver 论文调研驱动增强（Phase 6，第 §11 节）**——借鉴 WeBug (ICSE'22) / WeReplay (FSE'23) / MiniScope (arXiv'24) / VisionDroid (arXiv'24) 思路，新增"截图稳定性等待 + SSIM 基线对比 + WeBug 三条硬规则"，构建零业务侵入的 driver 自动化路径；在**两个独立小程序**（demo-uniapp + 新构造的 foreign-uniapp/ShopMart）上跑通真机 24-case 矩阵，learned_triage 跨小程序准确率完全一致（41.7%），WeBug R3 跨小程序更稳定（9→13 触发）

最终系统在自建 350 样本 benchmark 上实现 **90.3% 准确率 / 0.93 macro-F1**；在真实截图端到端验证中比规则法多正确分诊 2 例（14/14 vs 12/14）；Phase 6 离线 smoke + 真机两次矩阵共 62 个 case 显示：单通道 learned_triage 准确率收敛到 41-43%，多通道 OR 把覆盖率拉到 81-91%。陌生小程序矩阵首次为 driver 通用性提供真实证据。

## 1. 背景与问题定义

### 1.1 业务背景

测试人员在排查小程序问题时常常遇到"页面卡顿"、"图片模糊"、"数据显示错位"、"白屏"等表象问题。这些表象的根因可能落在三个完全不同的维度：

- **功能维度**：前端业务逻辑 bug、字段映射错误、状态同步失败
- **性能维度**：后端接口慢、内存压力、小程序运行时性能约束
- **视觉/渲染维度**：图片质量、布局错位、白屏黑屏、CSS 异常

把"性能触顶"误判为"代码 bug"或反之，会浪费大量排查时间。本项目要做的是构建一个能够把这些表象问题**自动归因到具体维度**的工具。

### 1.2 v1 阶段成果与不足

v1 阶段完成了：
- uni-app demo 小程序（3 个页面）
- 8 类故障注入机制
- FastAPI 诊断后端（OpenCV 视觉断言 + PaddleOCR 文本断言）
- minium-based 矩阵化测试（14 用例 × 多轮跑）

v1 的**核心断言决策逻辑**是一张手写的 8 行真值表：

```
| Afunc | Aperf | Avisual | Verdict          |
|-------|-------|---------|------------------|
| Pass  | Pass  | Pass    | Pass             |
| Pass  | Fail  | Pass    | PerformanceRisk  |
| ... 等
```

### 1.3 外部评审反馈

收到的 per-claim novelty 评估如下：

| Claim | 评级 | 主要冲突点 |
|---|---|---|
| C1 三路证据融合 | LOW-MEDIUM | LLMs-as-oracle、GUI invariants 已做多模态融合 |
| C2 显式 root-cause 分诊矩阵 | **MEDIUM** | 商业 ML 三类化做了粗分类，但未正式做这个框架 |
| C3 已知根因 fault profile benchmark | LOW | AndroFIT、Uber Chaos (2026) 工业规模 |
| C4 规则法视觉断言 | LOW | Owl Eyes / Nighthawk (ASE 2020/22) 用 DL 是 SOTA |
| C5 WeChat 小程序载体 | LOW | WeDetector / WeReplay / MiniScope 已占领 |

评审同时指出了 8 篇最近的 prior work（Owl Eyes、VisionDroid、Uber Mobile Chaos 2026、WeDetector、AutoConsis、GLIB、AndroFIT、GUI invariants）作为威胁。

### 1.4 v2 阶段的策略

针对评审反馈，v2 阶段不再试图在每个单点都比 prior work 强（不现实），而是：

- **砍掉竞争不过的 claim**：放弃"三路融合"和"小程序载体"作为独立 contribution
- **放大唯一的 MEDIUM**：把 C2 升级为可学习的维度化分诊
- **改造 C4**：从纯规则改为 cascade（规则 + MLLM 升级），把"规则法是 SOTA 退步"翻译成"成本-准确率权衡"
- **重构 C3**：从私有矩阵改为可复现的特征级 benchmark
- **新增工程价值**：把整套能力打成 SDK，可嵌入任意小程序——这是 prior work 没有覆盖的工程角度

### 1.5 项目定位 & 价值边界（项目能解决什么、不能解决什么）

**直面一个常见质疑**："性能 bug 开发者自己看代码就知道、视觉问题肉眼一看就明白，这个项目有什么用？"

这个质疑在**"开发者自测单页面"**的语境下是对的。本项目真正的应用场景是下面三个**人眼/源码自检解决不了**的场景：

| 场景 | 为什么自检不够 | Vision-Triage 的价值 |
|---|---|---|
| CI/回归批量巡检 | 一次提交 × 10 页面 × 8 profile = 80 张截图，人肉看一轮 30 分钟，看 100 轮就崩溃 | 80 张图 30 秒自动分类成 5 类 verdict，CI 红绿一目了然 |
| 黑盒验收 / 平台审核 | 微信平台审核团队、外包验收、跨团队 QA—**拿不到源码**，开发者的"代码自检"用不上 | 纯输入输出黑盒就能给出维度化分诊 |
| 灰度后线上巡检 | 上线 3 天后某机型偶发渲染异常，开发者已切下一个需求；每天人工看 100 张巡检图不现实 | 自动巡检 + 维度归因，直接 page 给对应方向（前端/后端/视觉） |

**项目的输入** （一次诊断 = 一个"现场快照"）：
- 一张页面截图（PNG，约 200KB）
- 性能指标（`{interaction_ms: 1200, memory_warnings: 0}`）
- 业务断言（`{visible_value: 7, expected_value: 10}`，可选）
- 上下文（`{page: feed, profile: blur_image}`）

**项目的输出**（结构化分诊单）：
- verdict ∈ {Pass, PerformanceRisk, RenderBug, FunctionalFail, Mixed}
- 三维异常分数（visual/perf/func）
- baseline 视觉回归证据（SSIM/pHash，v2 driver 新增）
- WeBug 三规则触发证据（v2 driver 新增）

**已知局限**：
1. 训练 14 个真实样本 + 386 合成样本，跨小程序泛化未经验证
2. 离线 smoke 显示 learned_triage 单通道准确率会随截图分布偏移而下降（见 §11.6）—— 需要多通道证据兜底
3. 功能维度必须开发者通过 `setExpected/setVisible` 注入语义；SDK 不可能猜业务期望

## 3. Phase 1 — 可学习的维度化分诊

### 3.1 设计

v1 的 `triage._decide_verdict` 只看 `(func_pass, perf_pass, visual_pass)` 三个布尔——这是一种**信息坍缩**：blur_score=80 和 blur_score=10 被同等地看作 "visual 失败"，但它们的不确定性差别巨大。

v2 把决策从 3 布尔扩展到 **18 维特征向量**：

| 模态 | 特征 |
|---|---|
| 视觉 | blur_score_full, blur_score_card, edge_density, mean_brightness, is_black_white, is_blur, ocr_text_len |
| 性能 | interaction_ms, memory_warnings, perf_pass |
| 功能 | func_visible_diff, func_has_overlap, func_is_blank, func_state_provided, func_pass |
| 上下文 | page_feed, page_counter, page_layout（独热） |

在这个 18 维特征空间上训练一棵**浅决策树**（max_depth=5）来做分类——这个深度保证可解释性，同时容纳跨模态的非线性边界。

### 3.2 训练语料

- **真实样本**：从 12 份历史 `auto_test_report_*.json` 挖出 63 条带 ground-truth 标签的样本
- **合成扩增**：对欠采样类做基于锚点的高斯加噪扩增，每类补到 80 条
- **最终训练集**：400 条，5 类各 80 条平衡

### 3.3 实验结果

#### 测试集（300/100 切分，stratified）

| 模型 | accuracy | macro-F1 |
|---|---|---|
| **Tree (max_depth=5)** | **0.910** | **0.906** |
| RandomForest | 0.870 | 0.864 |
| 规则法 baseline | 0.740 | 0.721 |

#### 真实截图端到端验证（14 样本，no synthesis）

把训练好的模型接进诊断主流程，在 14 张历史真实截图上跑：

| 引擎 | 正确 / 总数 |
|---|---|
| 规则法 | 12 / 14 (85.7%) |
| **Learned Tree** | **14 / 14 (100%)** |

规则法失败的两例分析：
- `feed/slow_api`：截图实际为黑屏（窗口未聚焦），规则法读到 `is_black_white=True` 后判为"视觉异常+性能异常"→ Mixed，但实际只有性能问题 → 期望 PerformanceRisk
- `feed/memory_pressure`：同上

Learned Tree 在这两例上之所以正确，是因为它在 18 维特征空间里学到了"当 interaction_ms=900 且 functional_pass=True 时，即使 visual_pass=False，verdict 也是 PerformanceRisk"这样的跨模态修正规则。

#### 模态消融（Ablation）

将每个模态的特征置为中性值，重新预测：

| 条件 | accuracy | macro-F1 | 主要塌陷的类 |
|---|---|---|---|
| 全部特征 | 0.910 | 0.906 | — |
| 去掉 visual | 0.680 (-23%) | 0.629 | RenderBug F1: 0.74 → **0.00** |
| 去掉 performance | 0.580 (-33%) | 0.497 | Mixed F1: 1.00 → **0.00** |
| 去掉 functional | 0.530 (-38%) | 0.432 | FunctionalFail F1: 1.00 → **0.00** |
| 只保留 visual | 0.380 | 0.293 | 大部分类塌陷 |
| 只保留 performance | 0.300 | 0.169 | 大部分类塌陷 |
| 只保留 functional | 0.400 | 0.236 | 大部分类塌陷 |

**结论**：每一种模态都不可替代——去掉任何一个，至少有一个 verdict 类的 F1 直接归零。这是对"三模态融合不只是堆砌"的实证。

### 3.4 特征重要性（RandomForest）

| 排名 | 特征 | 重要度 |
|---|---|---|
| 1 | func_pass | 0.154 |
| 2 | interaction_ms | 0.151 |
| 3 | perf_pass | 0.136 |
| 4 | blur_score_full | 0.116 |
| 5 | func_visible_diff | 0.077 |
| 6 | blur_score_card | 0.075 |
| 7 | memory_warnings | 0.054 |

前 7 个特征覆盖约 76% 的决策权重，分布在三个模态——再次说明"任一模态独占"的方案会丢掉至少 20% 的关键信息。

## 4. Phase 2 — Rule→MLLM 级联视觉 Oracle

### 4.1 动机

评审指出 C4（规则视觉断言）落后于 DL（Owl Eyes）。直接换成 DL 又有两个问题：

- 推理成本高（GPU 不可控）
- 调外部 MLLM API 有 ¥ 成本与延迟

v2 的折中：**cascade**——把规则当作便宜的 pre-filter，只在置信度低的"模糊带"升级到更强的 oracle。

### 4.2 升级判定

```python
if blur_score >= 400 and edge_density >= 0.08:    return confident_pass   # 不升级
if blur_score <= 30  and edge_density <= 0.02:    return confident_fail   # 不升级
if is_black_white:                                return confident_fail   # 不升级
else:                                             escalate_to_mllm        # 升级
```

### 4.3 强化 oracle 的两个实现

#### HeuristicMLLM（默认，无外部依赖）

在规则的 `cv2.Laplacian` 之外加：
- **多尺度 Laplacian**：金字塔降采样 3 级，取最小方差（更保守）
- **9-patch 投票**：3×3 划分，统计模糊 patch 数
- **HSV 饱和度均值**：低饱和度→褪色/部分白屏
- **Sobel 梯度峭度**：清晰图重尾分布、模糊图正态——亚像素模糊敏感

#### DashScopeQwenVL（可选，需要 API key）

把图像 + 一段强结构化 prompt 一起喂给 `qwen-vl-plus`：
```
你是一个小程序界面视觉异常检测器。请输出 JSON：
{"has_blur": bool, "has_blank": bool, "has_overlap": bool,
 "has_missing_image": bool, "confidence": 0-1, "reasoning": "..."}
```
估计成本约 ¥0.008 / 张。

### 4.4 实验结果（14 真实截图）

| Oracle | visual 准确率 | verdict 准确率（接 learned tree） | 平均延迟 | 升级率 |
|---|---|---|---|---|
| rule_only | 71.4% | 100% | 18.5 ms | 0% |
| **cascade** | 71.4% | **100%** | 30.9 ms | **57.1%** |
| heuristic_always | 71.4% | 100% | 23.3 ms | 100% |

在 14 样本规模上，三种 oracle 的 verdict 准确率都被 learned tree 抹平到 100%，所以 cascade 的真正价值在 **升级率指标**：57% 的样本被 cascade 判为"边缘需要复核"——这恰好是 v1 规则会出错的样本范围。

更大规模下（VT-Bench 350 样本，见 §5），cascade 与单一 oracle 的差异会清晰显示。

## 5. Phase 3 — VT-Bench v1：可复现的故障基准

### 5.1 设计目标

评审指出 v1 用的 14 用例样本量太小、且没有"边界样本"覆盖。VT-Bench v1 的目标是：

- **可复现**：固定 seed，任何研究者重跑都得到同样的数字
- **可扩展**：以 (page, profile, intensity) 为坐标轴，任意加新场景
- **覆盖边界**：每个 profile 都有从弱到强的强度档位，专门测 oracle 在"800ms 阈值附近"这种灰色地带的鲁棒性
- **特征级**：不依赖实跑小程序，直接合成特征向量——评测 oracle 把特征→verdict 的能力

### 5.2 规模与分布

- **14 个 (页面, profile) 场景** × **25 个强度档位** = **350 样本**
- **28.0% 边界样本**（intensity ∈ [0.35, 0.65]）
- **类别分布**：Pass=75, PerformanceRisk=125, RenderBug=25, FunctionalFail=75, Mixed=50

类别分布是**自然的故障注入分布**（PerformanceRisk 多因为 slow_api 是 page-agnostic 的；RenderBug 少因为只有 feed × blur_image 一个组合）——这种偏斜会暴露在小类上的 oracle 弱点。

### 5.3 评测结果

```
oracle            acc       macro_f1    borderline_acc
------------------------------------------------------------
rule              0.8800    0.8867      0.9898
learned_tree      0.8257    0.8373      0.9286
learned_forest    0.9029    0.9316      1.0000
```

#### 重要发现

**规则法在 VT-Bench 上的准确率（88%）反而比在训练测试集上（74%）更高**——因为 VT-Bench 是按规则语义生成的"干净"数据，规则法天然契合。这反映了一个关键观察：

> **训练分布与评测分布的不同，决定了哪一类 oracle 占优**：
> - 在**真实带噪样本**上（如 14 张实际截图），learned tree 强（14/14 vs 12/14）
> - 在**干净理想样本**上（VT-Bench），forest 强（0.90 vs 0.88）
> - tree 在 VT-Bench 上反而不如 forest，是因为它在训练时被合成噪声"过度正则化"了

这个发现的工程意义：**生产部署应该用 forest 做主引擎，但需要用真实带噪测试集做兜底**。

#### Per-class F1（最有信息量的对比）

| 类 | rule | tree | **forest** |
|---|---|---|---|
| Pass | 0.78 | 0.81 | 0.82 |
| PerformanceRisk | 0.84 | 0.76 | 0.84 |
| RenderBug | 0.81 | 0.96 | **1.00** |
| FunctionalFail | 1.00 | 1.00 | 1.00 |
| Mixed | 1.00 | 0.67 | **1.00** |

**RenderBug 上 forest 完胜规则法**（1.00 vs 0.81）——这是因为 forest 学到了用 `blur_score_full=120`（恰在 100 阈值之上）这种亚阈值信号判正确，而规则的硬阈值无法做到。这正面回应了评审"规则法不如 DL"的质疑。

### 5.4 边界样本表现

| Oracle | 边界样本准确率 |
|---|---|
| rule | 0.990 |
| tree | 0.929 |
| **forest** | **1.000** |

边界样本是真正考验 oracle 鲁棒性的地方——forest 在这里仍能保持 100% 准确率。

## 7. 与外部评审 prior work 的差异化

为防止"自说自话"，逐条说明本工作相对每篇威胁性 prior work 的 delta。每条都满足
"vs X，我的 delta 是 Y"的一句话测试——说不出 delta 的 claim 不成立。

### 7.1 小程序生态四篇（载体定位）

近三年小程序方向的代表作可分成两簇：**静态分析**（WeDetector/WeMinT/MiniScope）与
**重放基础设施**（WeReplay）。**没有一篇做"运行时多模态、维度级的故障分诊"**——这正是
Vision-Triage 占据的空格。其中 WeReplay 在**技术上最近**（同样在小程序 GUI 截图上用模型），
但**目的正交**（重放时序 vs 故障归因）。

| Prior Work | 他们做什么（核实后） | 我们的 delta |
|---|---|---|
| **WeDetector / WeBug** (ICSE 2022) | **静态**分析源码，检测 3 类固定 bug 模式：平台 API 误用 / 布局适配缺失 / 异步回调返回数据错配；25 个小程序找到 11 个未知 bug | **静态源码模式检测 → 运行时多模态维度分诊**。他们告诉你"这段代码有异步返回 bug 模式"，我们告诉你"这个**正在运行**的页面在功能维度失效"。互补：他们的异步返回规则被我们下放为运行时 WeBug-R3 功能通道 |
| **WeReplay** (FSE 2023) | 用**图像 DL 模型**判别 GUI **渲染状态**（渲染完/未完，P=92.1%/R=93.3%），服务于 record-and-replay 的**事件时序调度** | **渲染态判定服务于重放时序 → 视觉证据服务于故障归因**。同模态（截图）、反目的：他们答"页面渲染完了吗"，我们答"哪个维度坏了、为什么"。他们的发现反向印证我们"baseline 通道在异步/渲染抖动下失效"的观察 |
| **MiniScope** (TOSEM/arXiv 2024) | 两阶段**静态+动态混合**分析 + 自动 UI 探索，检测 MiniApp 的**隐私不一致** | **隐私一致性检测 → 运行时操作性故障分诊**（功能/性能/视觉），**正交的故障类**。我们借用其"自动 UI 遍历"思路驱动矩阵，但判定目标完全不同 |
| **WeMinT** (ASE 2023) | **静态污点分析** + AST 表示 + 异步回调建模，查敏感数据泄漏；20K 小程序中 36.5% 有泄漏 | **数据泄漏污点分析 → 运行时操作性故障分诊**。安全/隐私域，与本项目**完全正交、不重合**（故 Phase 6 调研中明确"未采纳"其方法） |

### 7.2 视觉/分诊/故障注入相关

| Prior Work | 我们的 delta |
|---|---|
| **Owl Eyes / Nighthawk** (ASE 2020/22) | 他们 detect 不 triage。我们的 verdict 进一步把视觉异常归入 RenderBug 或 Mixed，配合 perf/func 给出**维度级根因** |
| **Trident / VisionDroid** (2024) | 用 GPT-4V 输出自由文本判定，无 pre-MLLM 过滤。我们输出**离散** 5 类 verdict（能算混淆矩阵、能学习、能 ablate），且用 rule→Qwen cascade **只在歧义带**调用 MLLM——歧义带实验证实 cascade 用 1/4 成本达到 qwen-always 同等准确率 |
| **Uber 2026 Mobile Chaos** | 工业 180k 规模，做 **service-level RCA**（哪个后端挂）。我们做 **dimensional-level RCA**（哪个失效维度），二者正交互补 |
| **AutoConsis** (ICSE 2024 SEIP) | 只做数据不一致一类，相当于我们 wrong_mapping + stale_ui 子集 |
| **GLIB** (ESEC/FSE 2021) | 游戏场景、DL 视觉 oracle。我们覆盖更多模态 |
| **AndroFIT** (IEEE TR 2019) | 注 OS API delay 看用户体验，不做分诊判定 |
| **GUI invariants as GUI Oracles** (J.SS 2025) | 单模态。我们三模态 |

> 一句话定位：**WeDetector/WeMinT/MiniScope 在编译期/源码层找 bug 与隐私问题，WeReplay 解决重放时序，
> Owl Eyes/Trident 做视觉/功能 bug 的*检测*，Uber 做*服务级*归因——Vision-Triage 是唯一一个把
> 视觉+功能+性能三模态证据在*运行时*融合、产出*维度级离散 verdict*、且以*零侵入 driver* 接入任意小程序的工作。**

外部反馈指出：v2 阶段的 SDK 集成路径仍然要求每个页面 `useTriageProbe('name')` + 手写 `markInteractionStart/End` + `setExpected/setVisible`，实测集成成本 13.85% LOC。这对小程序开发者来说**仍然太重**——尤其是黑盒验收/平台审核场景，根本拿不到源码做这些埋点。

Phase 6 的目标是借鉴小程序领域近 3 年的 4 篇关键论文，把项目改造成**完全零侵入的 driver 自动化方案**。

### 11.2 论文调研（5 篇核心相关工作）

|---|---|---|---|
| **WeBug/WeDetector** | ICSE 2022 | 静态分析三类 bug：平台 API 误用 / 布局适配缺失 / 异步回调返回数据错配 | 把 3 类 bug pattern 写成**运行时**硬规则补丁 |

### 11.4 三个新模块的实现要点

**M1. stability_wait.py（参考 WeReplay）**
- 算法：每 200ms 截一帧，相邻两帧 SSIM 都 ≥ 0.985 持续 N 帧则判定稳定
- 与 WeReplay 区别：他们用 DL 模型 (P/R ~92%)；我们用 skimage.metrics.ssim，**零训练成本**
- 自测：模拟"前 800ms 抖动后稳定"场景，1190ms 收敛，SSIM 历史 `[0.33, 0.34, 0.34, 0.50, 1.0, 1.0]`

**M2. baseline_compare.py（工业级 SSIM+pHash 组合）**
- SSIM：结构相似度（Applitools/Percy 通用做法）
- pHash：32×32 FFT 实部低频块 + 中位数阈值
- 像素差占比：L1 差 > 25 的像素比例
- 经验阈值：SSIM<0.92 或 像素差占比>0.05 视为视觉回归
- 输出：三联可视化对比图（baseline / current / 差异热图）

**M3. webug_rules.py（WeBug 三类 bug 模式的运行时映射）**
- R1 `PLATFORM_API_MISUSE` → 运行时映射：交互后无视觉变化（pre/post SSIM>0.999）且 interaction_ms>1500ms
- R2 `INCOMPLETE_LAYOUT_ADAPTATION` → 运行时映射：DOM 优先看 scrollHeight>clientHeight，无 DOM 时用边缘带非背景像素比 >18%
- R3 `ASYNC_CALLBACK_DATA_MISMATCH` → 运行时映射：visible/expected 类型或值不匹配，或 DOM 中包含 `undefined`/`NaN`/`[object Object]`
- 6 个 case 自测全部通过

| 通道 | 在 14 个真实历史截图上的表现 |
|---|---|
| **A. learned_triage 单独** | verdict 准确率 **42.9%** (6/14) ⚠ |
| **B. baseline SSIM/pHash 单独** | 视觉回归触发 7 次（全部为真实故障） |
| **C. WeBug R1/R2/R3 单独** | 触发 4 次（全部为真实故障） |
| **A ∪ B ∪ C 多通道 OR** | **真实故障覆盖率 90.9%** (10/11 真实故障被至少一通道发现) |

**这是 Phase 6 最重要的发现**：

1. **训练分布外泛化下降是真实的**：learned_triage 在 VT-Bench 上是 91%，但跑历史截图掉到 42.9%。原因是训练数据里 perf 字段是模拟值，与历史截图的实际渲染状态不匹配。**这印证了 VisionDroid 论文的观察：单 MLLM 也只有 50-76% 准确率，需要 ensemble**。
2. **baseline 通道是独立证据**：它单独抓住了 7 个回归，其中 6 个是 learned_triage 漏判的——**这两个通道误差不相关，正适合 OR 集成**。
3. **WeBug 规则补功能维度盲点**：4 个 stale/wrong/mixed_fault 类故障 100% 被 R3 抓到，这是 SSIM/pHash 完全看不出来的（因为页面视觉上没变化，只是数据错）。
4. **多通道 OR 把覆盖率从 42.9% 拉到 90.9%**：唯一漏掉的是 `counter/slow_api`——纯接口延迟、最终页面视觉与基线无差、且 perf 阈值学得不准，三条通道全错过。这是 known limitation。

### 11.11 陌生小程序验证（foreign-uniapp / ShopMart）

为了证明 driver 路径**真的对"不是 demo-uniapp 的小程序"也能跑**（不只是宣传），构造了一个独立的对比小程序 `foreign-uniapp/`（项目名 "ShopMart"），与 demo-uniapp 共享业务接口但 UI 完全不同：

| 维度 | demo-uniapp | foreign-uniapp (ShopMart) |
|---|---|---|
| 应用主题 | 蓝色调技术风（#4A90D9） | 红色调电商风（#E94D5F 渐变 + 阴影 + 左侧粗边框） |

| 卡片布局 | 2 列宫格 | 1 列大卡片 + 左边框装饰 |

**陌生小程序 24-case 结果**（`auto_test/reports/v2_driver/foreign_matrix_20260520_094315.md`）：

| 指标 | demo-uniapp | foreign-uniapp |
|---|---|---|
| learned_triage verdict 准确率 | 41.7% (10/24) | **41.7% (10/24)** ← **完全一致** |
| baseline 视觉回归触发 | 8 次 | 0 次（首批截图时序 bug） |
| WeBug 规则触发 | 9 次 | **13 次** ← 跨小程序更稳定 |
| 多通道 OR 故障覆盖率 | 81.0% | 61.9% |

**核心发现 1：driver 的跨小程序通用性得到真实验证**

learned_triage 在两个 UI 完全不同的小程序上输出的 verdict 准确率**完全一致（41.7%）**。这不是巧合——它证明 driver 路径与具体小程序 UI 解耦，是真正"换个小程序就能跑"。

**核心发现 2：WeBug R3 规则跨小程序稳定**

stale_ui / wrong_mapping / mixed_fault 三类功能故障，在 demo 与 foreign 上**都是 100% 被 R3 抓到**。R3 的实现完全不依赖 UI（只看 visible/expected 业务断言），所以泛化最稳。这正好印证了 WeBug 原论文的判断：**"基于代码语义的规则比基于像素的检测更 portable"**。

**核心发现 3：WeBug R2 启发式在装饰性 UI 上误报**

foreign-uniapp 的 feed 页 8/8 case 都触发了 R2 (layout_overflow)。**原因：ShopMart 的红色渐变背景 + 左侧 8rpx 粗边框装饰**被 R2 的"边缘非背景像素比 > 18%"启发式误判为"内容溢出屏幕"。这是一个有意义的局限性：

- WeBug 原论文用**静态代码分析**精确判断布局适配 → 不会被装饰误导
- 我们用**运行时像素启发式** → 装饰元素干扰边缘统计
- **这恰好印证了 WeBug 论文 contribution 的价值**：静态分析在精度上确实优于运行时启发式

**核心发现 4：baseline 通道工程鲁棒性不足**

foreign 矩阵的 baseline 首批截图全部失败（minium 启动初期 screen_shot 偶发不写文件）。已加重试机制但效果不稳定，需要更鲁棒的截图等待（如 WeReplay 论文那样用 DL 模型判断"截图就绪"）。这条通道的工程化是未来工作。

### 11.12 Phase 6 真实数据点汇总

| 场景 | learned_triage 准确率 | baseline 触发 | WeBug 触发 | 多通道 OR 故障覆盖率 |
|---|---|---|---|---|
| 离线 smoke (14 case 历史截图) | 42.9% | 7 | 4 | 90.9% |
| 真机 demo-uniapp (24 case) | 41.7% | 8 | 9 | 81.0% |
| 真机 foreign-uniapp (24 case) | 41.7% | 0 ⚠ | 13 | 61.9% |

**真实结论**：
1. 三个场景下 learned_triage 准确率收敛到 41-43% —— 模型对未见 perf 分布的样本泛化能力有限，这是已知 limitation
2. WeBug R3 是最 portable 的通道，跨小程序稳定
3. baseline 通道工程化未达成熟，需要 DL 模型加持
4. 多通道 OR 仍是必要的：单通道 41.7% 在所有场景下都不可用，但加上 WeBug R3 后功能故障 100% 被捕获

# 第一部分　汇报讲稿（口语化，可照念）

## 0. 开场：这个项目在做什么（约 1 分钟）

各位老师好。我们做的是一套**小程序故障检测与根因诊断系统**，名字叫 Vision-Triage。

一句话讲清楚它要解决的问题：小程序上线后会出各种"非崩溃"故障——图片模糊、白屏、数据显示错、布局错位、接口慢。这类故障**不会让程序崩溃**，传统的"看有没有报错/崩溃"的监控完全发现不了，但用户一眼就能看出来不对。

我们的思路是：**像人一样从外部观察页面**，把证据分到三个维度去判断——**视觉（Avisual）、功能（Afunc）、性能（Aperf）**，这就是我们说的"三轴分诊"。判断出有故障后，再进一步**定位到出问题的源文件、甚至源码行**，告诉开发者去哪儿改。

## 1. 中期回顾：当时其实只是 demo 上的简单缝合（约 1.5 分钟）

先诚实地回顾中期，这样大家能看清我们后面到底做了什么。

中期那版，标题叫《基于视觉感知的小程序性能根因诊断系统》，当时的状态是这样的：

- **载体只有一个我们自己写的 demo 小程序**（demo-uniapp，就图片流、计数器、布局三个板块）。
- **"三重断言分诊"当时只是一个概念**——决策矩阵是开题时的预想，还没有真信号驱动。
- **性能数据是硬编码推断的，写死 900ms**。这一点中期我们自己就在 PPT 里列为问题："未覆盖真实交互耗时"。
- **layout 重叠检测模块虽然写了，但没有接进 triage 决策**，也是我们自己列的缺口。
- **实测规模非常小：自动化只跑了 3 项测试，2 个成功（slow_api、memory_pressure），1 个失败（blur_image）**，blur 阈值当时还要再精调。
- 当时**没有：真实的第三方 app、没有源码变异基准、没有统计置信区间、没有根因定位的实测、没有跨页、也没有任何诚实的负结果**。

所以坦白讲，中期是"概念 + 一个 demo 上的简单缝合 + 3 个零散测试"。下面讲的，就是我们在这个基础上做了哪五件事。

## 2. 五点增量（核心，约 5 分钟，每点都带真实数字）

### 增量一：从自家 demo → 真实第三方开源 app + 源码变异基准 + 置信区间

我们不再只测自己的 demo。我们拿了**两个真实的开源小程序**：一个是 uni-app 编译的"小兔鲜儿"，一个是原生 WXML 的"youzouzou"。

故障是怎么造的？我们直接**改它们的源码**做变异注入——把字段名改错、把图片打糊、把布局搞溢出。**改了源码就等于自带了标准答案**（这是软件工程里公认的变异即真值方法，Just 等人 FSE'14）。然后配一组健康对照、混在一个池子里盲测，再用 bootstrap 算 95% 置信区间。

最有代表性的是 A 线——H5 随机大样本：20 个故障 + 5 个健康，结果是 **检出率 50%，置信区间 [30%, 70%]，健康页假阳 0%**。对照只看崩溃的 crash-only 基线，在同样这批故障上是 **0%**——一个都抓不到。

对比中期：中期是 3 个零散测试、性能 900ms 硬编码、准确率"待补充"；现在是**可复现的 50%[CI 30–70%] / 0 假阳**这种带不确定性的真实数字。

### 增量二：从"三重断言概念" → 真信号驱动的三轴分诊

中期 perf 是写死的、layout 没接进决策。这一阶段我们把三轴**用真信号喂起来了**。

特别是 C 线——devtools 真机路径，我们用 minium 零侵入连上真机，读的是**真实的 `page.data`、真实的 `wx.getPerformance`、元素真实几何（scrollWidth）**。在 youzouzou 上：7 个故障 + 2 个健康，**ours 多通道检出 71.4%（5/7），健康假阳 0%**。而且 layout 模块现在**已经接进决策**了。

这条线还有个有意思的对照：纯看崩溃的 crash-only 在那些纯色页面上**健康假阳高达 50%**——它会把好页面误报成坏的；而我们 ours 是 **0 假阳**。这说明多通道融合既能抓到，又不乱报。

### 增量三：从规则匹配 → 源文件 / 源码行级根因定位（本轮全新）

中期只能"判断有没有故障"，定位是空白。这一阶段我们补上了**确定性的根因定位，全程不调 LLM**。

- **视觉故障 → 源文件**：通过 bbox 面积排序定位，**文件级 8/10 = 80%，组件级 9/10 = 90%**。
- **功能故障 字段 → 源码行**（给定坏字段名时）：**5/5 = 100% 精确命中**。
- **page.data 坏字段 → 源码行的端到端闭环**：离线合成 **4/4 = 100%**，且**真机已验证通过**（minium 连 devtools 注入-抓取-恢复，见 Q11）。

视觉定位是我们迭代了三步才到 8/10 的：一开始用 class 匹配是 **0/10**（被 uni 框架的 wrapper 类污染），换成 data-v hash + 单点是 **4/10**，最后改成 bbox 面积排序才到 **8/10**。这里关键的两个修法是：用每个 .vue 唯一的 **data-v hash**（hash→文件 6/6 全对），加上**用 bbox 面积排序代替单点取样**。

### 增量四：从单 demo 单截图 → 双路径架构 + 跨页 + 每页稳定性门控

中期只有一个 demo、一条截图通道。现在我们是**一个诊断引擎 + 两条取信号路径**：

- **路径①（不用 devtools / 走 H5）**：Playwright 无头渲染，全自动、能大样本，但有数据和性能盲区。
- **路径②（用 devtools / 真机）**：minium 零侵入只读，能补上 page.data 和真几何的盲区，代价是样本小、要手动开开发者工具。

两条路**互补盖盲区**。另外我们加了跨页（D 线，index/cart/my 三页），以及**每页稳定性门控**——三页干净渲染两两分块 SSIM 全 = 1.0，证明我们的 0 假阳不是碰巧。

### 增量五：从无评测 → 一批诚实的负结果（方法学严谨的体现）

这点我想特别强调，因为我们没有藏问题。我们实测出三个**负结果**：

- **H5 零侵入测不出性能阻塞**：往 onLoad 注入 1.4 秒阻塞，同一注入两次墙钟 delta 是 1359ms vs 172ms——**方差比注入量还大，不可复现**；headless 的 Long Task API 对 1.4s 阻塞只报约 80ms。结论：H5 零侵入下，**性能维就是盲区**。
- **跨构建混用会全假阳**：旧 build 的基线对新 build 的渲染整图 SSIM 只有约 0.49。已修（强制同构建取样），同会话 FPR 是 0%。
- **Qwen-VL 单图有系统性偏见**：对带纹理的占位图，**每一张（包括健康基线）都判成缺图**，所以"100% 检出"是假象、健康页 100% 误报。

这些负结果不是失败，恰恰是我们方法学严谨的证据。

## 3. 现场可展示的成果（约 1 分钟）

如果现场要看，我们可以展示：

- **四条证据线的产物报告**（A/B/C/D 线，每个都有时间戳目录的 JSON，可逐字段核对）。
- **根因定位的产物**：视觉 8/10 文件级、字段→行 5/5 实测行号（比如 XtxGuess 的 item.name 定位到 L64、item.price→L67）。
- **工程质量**：`diagnosis/tests/run_all.py` 跑出 **82/82 全过**。
- 所有数字都能从产物 JSON 复现，源码变异本身就是标准答案。

## 4. 收尾（约 30 秒）

总结一下：中期我们交的是一个概念加一个 demo 上的简单缝合；这一阶段，我们把它落到了**真实 app + 真信号 + 源码级定位 + 双路径 + 诚实评测**。

我们最想传达的态度是：**所有数字都可复现、不夸大，能抓到的就说抓到（50% / 71.4% / 8/10），抓不到的就诚实说是盲区（性能维、Qwen 检测通道）。** 这套东西现在已经能做到"报警即指向对的子系统、并定位到源文件/行、且 0 假阳"——这是它能进 CI 的基础。谢谢各位老师。

# 第二部分　答辩预演：预期老师疑问 + 准备回答

> 每个回答都落到 FACTS 数字，并主动坦白负结果。

## Q1　检出率才 50%，是不是太低了？

**A：** 这是一个诚实的数字，而且要和对照一起看。在 A 线（20 故障 + 5 健康）上，纯看崩溃的 **crash-only 基线是 0%**——传统监控这类非崩溃故障一个都抓不到，我们是 50%，是从 0 起步的实质提升。而且我们的 **健康假阳是 0%**——不乱报。

50% 没更高，主要是**召回受小面积故障限制**：一些故障改动的区域太小，分块 SSIM 抓不到。我们没有为了好看去调参刷分，给的是带 **95% 置信区间 [30%, 70%]** 的真实分布。换句话说，我们宁可报一个诚实的 50%，也不报一个不可复现的高分。

## Q2　样本只有 N=20，结论可信吗？

**A：** 正因为样本不大，我们才**用 bootstrap 给出 95% 置信区间 [30%, 70%]**，把不确定性明明白白标出来，而不是只甩一个点估计。

更重要的是我们做了**四条线交叉验证**，不是孤证：
- A 线（H5 随机大样本，小兔鲜儿）：50% [CI 30–70%]，假阳 0%；
- B 线（H5 手挑，小兔鲜儿）：60%，假阳 0%；
- C 线（devtools 真机，youzouzou）：71.4%，假阳 0%；
- D 线（跨页）：2/5 检出，健康 0/12 假阳。

四条线**载体不同、路径不同，但结论一致：能抓到一部分真故障、且几乎不假阳**。这种跨设置的一致性，比单条线 N 大更有说服力。

## Q3　中期不就有多通道了吗？这阶段到底新做了什么？

**A：** 中期的"多通道"是在**自家 demo** 上、perf 还**硬编码 900ms**、layout **没接进决策**的概念缝合。这阶段实打实新增的是五件：

1. **真实第三方 app + 源码变异基准 + bootstrap CI**（demo → 小兔鲜儿 / youzouzou，3 个零散测试 → A 线 50%[CI30–70%]/0 假阳）；
2. **真信号驱动的三轴分诊**（perf 接真 wx.getPerformance、读真 page.data、真几何，layout 已接入决策）；
3. **源文件 / 源码行级根因定位**（视觉 8/10、字段→行 5/5、page.data 闭环 4/4）——中期完全没有；
4. **双路径架构**（H5 + devtools 互补）+ 跨页 + 每页稳定性门控；
5. **一批诚实负结果**（Qwen 偏见、性能盲区、跨构建 FPR）。

## Q4　Qwen 到底用上了吗，效果怎么样？

**A：** 用上了，但我们得出的是一个**诚实的负结果**。

Qwen-VL **单图**判断对带纹理的占位图有**系统性偏见**：每一张——**包括健康基线**——都判成"缺图"。所以它表面上"100% 检出"其实是**无脑全报警的假象**，而且**健康页 100% 误报**。

我们试了**差分融合**（图 + 基线 + 代码一起喂），确实**消除了偏见**，但又**太保守，recall 只有 30%**。

所以结论很明确：**Qwen 目前不能用作视觉检测通道**。它正确的定位应该是"对已经定位好的区域做解释"的解释器，而不是检测器。这个我们如实写进了报告。

## Q5　根因定位 8/10 可靠吗？是怎么算出来的？

**A：** 链路是**确定性的、不调 LLM**：分块 SSIM 最低的 tile 集合 → 和页面所有元素的 getBoundingClientRect 求交叠面积 → 取面积最大且非根容器的元素 → 拿它的 **data-v hash** → 映射回 .vue 源文件。

为什么靠谱：**data-v hash 每个 .vue 唯一、不会撞车，hash→文件 6/6 全对**；再加上 **bbox 面积排序**而不是单点取样（单点容易命中相邻元素或大容器）。

迭代过程很能说明问题：用 class 是 **0/10**，hash + 单点是 **4/10**，hash + bbox 才到 **8/10 文件级、9/10 组件级**。

剩下没命中的，原因主要是**过定位（over-detected，圈到了相邻/包裹元素）**和个别小面积故障。我们没有把 8/10 说成 10/10。

## Q6　性能问题为什么检不出、也定位不了？

**A：** 这是我们诚实标出的盲区，是实测 **R1 负结果**：H5 零侵入下，往 onLoad 注入 1.4 秒阻塞，墙钟 time-to-content 同一注入两次是 **1359ms vs 172ms，方差比注入量还大、不可复现**；headless 的 Long Task API 对 1.4s 阻塞只报约 **80ms**，FCP 也不变。所以 **H5 零侵入测不到主线程阻塞**。

要做到性能定位，需要别的手段：CDP Profiler（Playwright 的 newCDPSession 能驱动）配 source-map 可以给到函数 + 行级，是确定性的——**但前提是 H5 先能检到（现在卡在盲区）**；而原生微信那边的深度 CPU profiler 是 **GUI-only，minium 拿不到**。这就是**平台不对称**：原生路径能拿结构化的 page.data、H5 路径拿不到。我们如实说明了边界。

## Q7　和 OwlEye / Applitools 这类视觉测试有什么不同？

**A：** 三点不同：
1. **DOM 锚定做源文件级定位**：它们大多停在"像素不一样了"，我们再往下走一步，通过 data-v hash 把视觉异常**锚定回 .vue 源文件**（8/10），甚至功能故障**定位到源码行**（字段→行 5/5）。
2. **双路径**：我们同时有 H5 无头路径和 devtools 真机路径，互补盖盲区；纯视觉对比工具只有截图一条路。
3. **诚实评测**：我们用源码变异即真值 + 配对健康对照 + bootstrap CI，并主动报告负结果（性能盲区、Qwen 偏见），不挑数据。

## Q8　H5 路径和 devtools 路径，是不是冗余了？

**A：** 不冗余，是**互补盖盲区**。
- H5 路径全自动、能大样本，但有**数据盲区和性能盲区**；
- devtools 路径能读 **page.data 和真几何**，正好补上 H5 截图漏掉的数据/几何故障，代价是样本小、要手动开开发者工具。

C 线就是证据：devtools 路径抓到了 H5 截图漏掉的数据/几何故障（ours 多通道 71.4%，其中 devtools-only 子通道 57.1%）。两条路覆盖的故障类型不一样，所以是补集关系。

## Q9　这东西对真实开发测试到底有什么用？

**A：** 三个实际价值：
1. **报警即指向对的子系统**——不是只说"有问题"，而是分到视觉/功能/性能哪一轴；
2. **定位到源文件 / 源码行**——视觉 8/10 到文件、字段→行 5/5 到行，开发者能直接去改；
3. **0 假阳可以进 CI**——四条线健康假阳都是 0%（A/B/C 的健康假阳 0%、D 线 0/12），不会天天误报骚扰开发者，这是能进流水线的前提。

而且**源码变异即真值、产物是 JSON 可复现**，适合做回归巡检。

## Q10　这些数字是真的吗？怎么复现？

**A：** 可以复现，而且真值是**机器自带的**：
- 故障是**直接改源码注入**的，所以**改了什么、就是标准答案**（变异即真值，Just et al. FSE'14），不存在人为标注偏差；
- 每条线都有**带时间戳的产物目录和 JSON**（A 线 campaign_20260531_033057、B 线 bench_report_20260530_214801、C 线 native_report_20260531_010859、D 线 crosspage_20260531_061419），可以逐字段核对；
- 工程侧 `diagnosis/tests/run_all.py` **82/82 通过**；
- 定位链路 grep 确认**零 LLM 调用**，是确定性的，跑一次和跑十次结果一样。

我们写报告时还专门维护了一份"已核实事实清单"，**每个数字都从产物 JSON 逐字段读出**，对不上的一律写"未测"。

## Q11　minium 的字段定位在真机上验证过了吗？

**A：** 这点我必须**诚实**：目前 page.data 坏字段 → 源码行的**端到端闭环是 4/4 = 100%，但用的是离线合成的 page.data**，不是真机抓的。

平台上有个不对称：在 minium 原生路径下，page.data 是结构化的，能直接拿到坏字段名（我们在 `devtools_probe.collect_data` 里加了 `suspicious_fields` / `broken_field_paths`），所以原理上**把合成数据换成 minium 真机的 page.data 就是真正的端到端**；而 H5 prod 编译把 `{{ }}` 编没了、Vue 的 per-node 实例也拿不到，**H5 路径的字段名运行时恢复仍是缺口**。

所以现状是：**离线合成闭环 4/4 已通，真机验证是明确的待办项**，我没有把它说成已经在真机跑通。

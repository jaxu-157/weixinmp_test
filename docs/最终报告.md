## 摘要

跨端小程序（uni-app / 微信原生）在生产中大量出现**非崩溃故障**——页面不报错、不闪退，却出现图片缺失、布局错位、数据绑定为空、加载迟缓等问题。传统崩溃测试与 lint 门禁对这类故障**结构性失明**：没有异常抛出，就没有信号。本项目提出 **Vision-Triage**，一个面向小程序非崩溃故障的**检测 + 维度级根因分诊（triage）**系统：它不只回答"页面坏没坏"，还把故障归到**视觉渲染 / 布局 / 数据-功能 / 性能**这些开发者可直接行动的维度，并进一步把根因定位到具体**源文件 / 源码行**。

系统采用**一个诊断引擎 + 两条取信号路径**的架构：路径①基于 Playwright 无头渲染（H5），可大样本全自动；路径②基于 minium 零侵入只读真机信号（devtools），补 H5 的数据/几何盲区。评测严格遵循"**真实第三方开源 app + 源码变异即真值（Just et al., FSE 2014）+ 配对健康对照 + bootstrap 95% 置信区间**"的可辩护协议。

四条独立证据线的关键结果（全部实测）：A 线（H5 随机大样本，N=20）以 **0% 健康假阳**检出 **50%**（bootstrap 95% CI **[30%, 70%]**）故障，检出即维度判对 **8/10**；B 线（H5 手挑，10 故障）检出 **60%**、条件 RCA **5/6**；C 线（devtools 真机，7 故障）多通道检出 **71.4%**、条件 RCA **3/5**；常规崩溃测试在 A/B 线检出 **0%**，在 C 线虽检出 **42.9%** 但健康页假阳高达 **50%**。根因定位上，视觉 tile→bbox→源文件 **8/10 文件级、9/10 组件级**；功能"字段→源码行"**5/5**；page.data 坏字段→源码行端到端闭环 **4/4**。工程上测试 **82/82** 通过。同时诚实报告三类负结果（Qwen-VL 系统性偏见、H5 性能维盲区、跨构建基线导致的假阳），它们正是方法学严谨的体现。

核心结论有二，且都有数据支撑：(1) 常规崩溃测试对非崩溃故障近乎全盲；(2) 一旦检出，维度归因高度可靠——这正是 triage 相对纯检测的真价值。

## 1. 研究问题与背景

### 1.1 小程序非崩溃故障的检测难题

小程序（微信原生、uni-app 跨端等）是国内移动前端的主力形态。其生产故障中，**真正崩溃的只是少数**；更常见的是页面"看起来在跑、实际上坏了"的非崩溃故障：

- **视觉渲染类**：图片加载失败/缺图、内容模糊、黑白屏、占位符；
- **布局类**：元素遮挡、错位、宽度溢出、文本截断；
- **数据-功能类**：数据绑定为空、字段名写错渲染出 `undefined`/空串、接口失败；
- **性能类**：主线程阻塞、加载迟缓导致内容迟迟不出。

这类故障的共同特征是：**没有异常抛出**。代码照常执行、Promise 照常 resolve，只是渲染出的像素/数据是错的。

### 1.2 为什么崩溃测试不够

主流 CI 质量门禁建立在"有异常即失败"的假设上：崩溃上报、错误监控、lint、单元/E2E 断言（断言通常也只覆盖逻辑分支，不覆盖视觉效果）。对上述非崩溃故障，它们**零覆盖**——这是真实的工程空白。

本项目用实验直接量化了这一空白：在我们的真实 app 源码变异基准上，"只看崩溃/JS 异常/黑白屏"的 crash-only 基线，在 H5 大样本上检出率 **0%**（A 线、B 线），在真机上虽达 **42.9%** 却以 **50% 的健康页假阳**为代价（C 线，详见 §5）。也就是说：崩溃测试要么漏掉几乎所有非崩溃故障，要么靠"乱报"凑检出。

### 1.3 本项目要回答的研究问题

- **RQ1（检测）**：能否在真实小程序上，以**零/低健康假阳**为约束，检出常规崩溃测试漏掉的非崩溃故障？
- **RQ2（分诊）**：一旦检出，能否可靠地把故障归到正确的**根因维度**（视觉/布局/数据-功能/性能）？这是相对"只判 pass/fail"的纯检测工作的关键增量。
- **RQ3（定位）**：能否把根因进一步收敛到**具体源文件 / 源码行**，且全程确定性、不依赖大模型？
- **RQ4（边界）**：这套方法在哪些情形下**失效**（负结果），平台之间存在哪些不对称？

### 1.4 相对中期的定位

中期工作（标题《基于视觉感知的小程序性能根因诊断系统》）已提出**三重断言分诊**概念——功能断言 Afunc / 性能断言 Aperf / 视觉断言 Avisual，并视"决策矩阵"为开题预想。但中期仅在自建 demo 小程序（demo-uniapp 的 feed/counter/layout 三板块）上验证，性能数据为**硬编码推断（900ms）**，layout 重叠模块已开发但**未接入 triage 决策**，自动化仅跑了 **3 项测试（2 成功、1 失败）**，且**没有**真实第三方 app、源码变异基准、统计置信区间、根因定位实测、跨页与诚实负结果。本报告把概念落地为**真信号驱动的可辩护系统**，并以真实数字取代硬编码与"待补充"。

## 2. 相关工作与差异化

Vision-Triage 的主张落在 **Detection 与服务级 RCA 之间的中间层**：比"判是否有问题"多了**维度归因**，比"归因到后端服务/RPC"更贴近 GUI 前端故障的开发者分诊场景。下表说明最相关的三类工作及差异。

| 相关工作 | 核心做法 | 与 Vision-Triage 的差异 |
|---|---|---|
| **OwlEye** | 用 Grad-CAM 在截图上给出 UI 显示问题的**热力图**，**无 DOM 锚定** | 它只产热力图、停在像素层，不做维度归因，也无法落到源文件；我们用 data-v hash 把像素 tile 锚回 DOM 元素与 `.vue` 源文件 |
| **WebSee / XFix** | 把视觉差异**区域→页面元素 / CSS 属性**逆映射，是"区域→元素"定位的**学术蓝本** | 思路同源（区域→元素），我们在小程序/uni-app 场景落地，并补"功能字段→源码行""page.data 闭环"两条非视觉定位链 |
| **Applitools RCA** | 商业视觉测试，**DOM 锚定**做根因分析，但**闭源** | 能力对标但不可复现/不可二次开发；我们给出开源、确定性、零 LLM 的等价定位链路 |

此外，评测方法学借鉴：Nighthawk 的**逐类目 P/R/F1 报告**；Trident 的**消融即说服力 + injection dataset 避免大模型训练重叠**；Uber Chaos 的**配对控制基线 + precision@k/Top-1**；WeBug 的**多源 GT + 真实第三方小程序 + 假阳成因诚实记录**；以及 **Just et al. (FSE 2014)** 的核心效度背书——**变异体检出能力与真实缺陷检出能力在控制覆盖率后仍统计显著相关**，故变异体是真实缺陷的**有效代理**。这条背书是我们"源码变异即真值"协议的合法性基础（详见 §4.5、§6）。

> 术语纪律：本文始终用 **triage / 维度归因**措辞，避免与纯 detection 工作做不公平的精度直接对比。

## 3. 方法

### 4.1 架构：一引擎两路径

> （编号沿用任务规格，下同。）

Vision-Triage 是**一个诊断引擎 + 两条取信号路径**，而非两套独立系统。

- **诊断引擎**（三轴分诊核心）：`fault_bench/vt_diagnose.py` 与 `diagnosis/diagnose/triage.py`，对每个被测页面给出三轴判定——**视觉 / 功能 / 性能**。
- **路径①「不依赖 devtools / H5」**：`fault_bench/bench/renderer.py` 用 Playwright 无头渲染 uni-app 编译出的 H5，配合 `run_campaign.py`。信号 = **分块 SSIM（8×3 网格，阈值 0.85）+ 整图 SSIM + DOM 几何**。承载 A / B / D 三条证据线。优点是全自动、可大样本；代价是存在数据/性能盲区。
- **路径②「依赖 devtools / 真机」**：`auto_test/v2_modules/devtools_probe.py` 通过 minium connect **零侵入只读**接入真机。信号 = **`page.data` + `wx.getPerformance` + 元素真几何 `scrollWidth`**。承载 C 线。优点是补数据/几何盲区；代价是样本小、需手动开启开发者工具。

两路径**互补**：H5 可大样本但盲于运行时数据与主线程阻塞；devtools 能拿到结构化数据与真几何，但难以规模化。

### 4.2 检测：多通道证据

引擎在每个页面上并行运行多条检测通道，取并集驱动报警：

- **分块 SSIM**（本项目主力、可辩护通道）：把页面切成 8×3 网格，逐 tile 与同构建基线比对，任一 tile 低于阈值 0.85 即视为局部变化。它是**确定性**的、不依赖 DOM/性能，对长滚动页里的**局部**改动敏感。
- **整图 SSIM**：原有通道，对整页做一次 SSIM。长页里局部改动会被整页稀释（见 §5 A 线对比）。
- **WeBug 风格规则**（`auto_test/v2_modules/webug_rules.py`）：R2 像素/几何溢出启发式、R3 可疑 token 扫描（`undefined`/`null`/`NaN`/`[object Object]`/真实 DOM 文本里的 `{{`）。
- **learned 五分类 verdict**：可选加权器。实测发现它对输入特征是否完整**不稳定**（传/不传 `dom_info` 判定会翻转），故**不进 headline**，检出率以稳定图像通道为准（详见 §5 负结果与局限）。

> 设计原则：**检出率必须与健康假阳一起报**。任何只报 recall 不报 FPR 的通道都不可信（Qwen-VL 负结果即此教训，§5）。

### 4.3 三轴分诊

通道证据汇入诊断引擎，按**视觉 / 功能 / 性能**三轴给出维度判定（对应中期"三重断言"Avisual/Afunc/Aperf 的真信号落地版本）：

- **视觉轴**：分块/整图 SSIM 局部下沉、模糊/黑白屏/遮挡规则；
- **功能轴**：`page.data`/DOM 文本里的坏字段 token、空绑定、接口失败；
- **性能轴**：`wx.getPerformance` 等加载/时序信号（当前为部分盲区，见 §5）。

报警时不仅给"坏了"，还给"坏在哪一维"，把开发者排查成本从"全页排查"降到"按维度排查"。

### 4.4 根因定位：从"哪一维"到"哪个源文件 / 行"

本轮把分诊从维度推进到**源文件 / 源码行**，**全程确定性、零 LLM 调用**（已 grep 确认无大模型调用）。

**(a) 视觉/布局：tile → bbox → data-v hash → 源文件**

```
分块 SSIM 低于阈值的 tile 集
  → 与所有元素 getBoundingClientRect 求交叠面积
  → 交叠面积最大且非根容器的元素
  → 其 data-v hash → .vue 源文件
```

两个关键设计：
- **用 data-v hash 而非 class 做映射**：uni-app 框架的 wrapper 类（如 `navigator-wrap`/`scroll-view`）会污染 class 索引；改用从 dist scoped CSS 解析的 `data-v-*` hash，每个 `.vue` 唯一、不撞车，hash→文件映射全对。
- **bbox 面积排序替代单点采样**：单点 `elementsFromPoint(tile 中心)` 易命中相邻元素/大容器；改为"在所有变化 tile 的并集框内取交叠面积最大、非根容器、hash 可映射的元素"，大幅修掉"最差 tile 选错位置"。

**(b) 功能：坏字段名 → 源码行**

功能故障比视觉更直接——**坏字段名本就被运行时命名**（minium `page.data` 直接列出空/`undefined` 的 key；或 ajv/zod 从 API 契约的 `instancePath`）。拿到字段名后，"字段→源码行"是纯静态解析：`build_field_line_index` 扫描每个 `.vue` 的 `<template>`，把每个绑定（`{{ item.x }}` 与 `:attr="item.x"`）映射到行号，`resolve_field_line(文件, 字段)` 直接查行。

**(c) page.data 坏字段 → 源码行（端到端闭环）**

把 (b) 与运行时数据层打通：从 `page.data` 取出坏字段路径，经字段→行索引直接落到源码行。该闭环**已在真机验证通过**——minium 连 devtools 实读 youzouzou 真实 `page.data`，注入坏字段后扫描器正确指名 `list[0].id`，恢复后干净（见 §5.4 与 `datafield_live_inject.json`）。

### 4.5 评测协议

评测严格遵循**可辩护协议**（详见 `docs/EVALUATION_PROTOCOL.md`）：

1. **真实第三方开源 app**：H5 路径用开源 uni-app **小兔鲜儿**；真机路径用开源**原生 WXML youzouzou**。均**非作者编写**，规避"在自己熟悉的 app 上过拟合"。
2. **源码变异即真值**：把正确源码改成常见开发者错误（改色、缺图、宽度溢出、字段置空等），编译运行。**根因维度天然已知**（因为我们知道注入了什么），即 ground truth。理论背书：**Just et al. (FSE 2014)**——变异检出与真实缺陷检出统计显著相关。
3. **配对健康对照**：每个变异都保留注入前的同构建基线截图，供 SSIM 差分与"是否真故障"判定使用；**基线与被测样本必须来自同一次构建/渲染**（跨构建混用会全假阳，见 §5 负结果 R2）。
4. **混合池 + bootstrap 95% CI**：故障样本与健康样本混入同池测假阳；检出率由 bootstrap 重采样给出 95% 置信区间，而非单点估计（N 小，点估计不可靠）。

## 5. 实验结果与分析

### 5.1 四条证据线总览

| 证据线 | 产物文件 | 载体 | N | ours 检出 | 健康假阳 | crash-only | 条件 RCA（检出即对） |
|---|---|---|---|---|---|---|---|
| **A. H5 随机大样本** | `campaign_20260531_033057` | 小兔鲜儿 uni-app | 20 故障 / 5 健康 | **50%** [CI 30–70%] | **0%** | **0%** | **8/10 = 0.80** |
| **B. H5 手挑** | `bench_report_20260530_214801` | 小兔鲜儿 | 10 故障 / 3 健康 | **60%** | **0%** | **0%** | **5/6 = 0.833** |
| **C. devtools 真机** | `native_report_20260531_010859` | youzouzou 原生 WXML | 7 故障 / 2 健康 | **71.4%** | **0%** | 42.9%（健康假阳 50%） | **3/5 = 0.60** |
| **D. 跨页** | `crosspage_20260531_061419` | index/cart/my | 5 故障 / 12 健康 | 2/5 检出 | **0/12** | — | 2/2 |

**逐线分析：**

- **A 线（主证据）**：在 20 个穷举生成的变异上，**多通道检出 50%、健康假阳 0%**，bootstrap 95% CI **[30%, 70%]**。这是带统计置信区间的主数字。50% 不是高分，但它建立在 0 假阳约束与无偏穷举之上，且 **crash-only 在同基准检出 0%**——直接量化了崩溃测试的全盲。条件 RCA **8/10 = 0.80** 说明：在被检出的故障里，维度归因高度可靠。
- **B 线（手挑互补）**：与 A 线同 app，结论一致——检出 **60%**、健康假阳 **0%**、crash-only **0%**、条件 RCA **5/6 = 0.833**。手挑样本检出率略高于随机大样本，符合预期（手挑偏向可见后果明显的故障），但维度归因可靠性与 A 线同量级，互相印证。
  > 订正说明：本线条件 RCA 为 **5/6=0.833**（旧版报告曾误写 6/6）；本文以核实真值为准。
- **C 线（真机互补，补盲区）**：在原生 WXML 上，**ours 多通道检出 71.4%、健康假阳 0%、条件 RCA 3/5 = 0.60**。它补的是 A 线的两类盲区——`page.data` 抓**无像素特征的数据故障**、`scrollWidth` 真几何抓**布局溢出**。关键对照：**crash-only 在 C 线检出 42.9%，却以健康页 50% 假阳为代价**（纯色页骗过黑白屏检测），反衬 ours 的 0 假阳。
  > 订正说明：C 线 ours **多通道**检出为 **71.4%**；其中 **devtools-only 子通道才是 57.1%**（旧版把 57% 误当作 C 线检出）；条件 RCA 真值为 **3/5=0.60**（旧版误写 4/4）。本文以核实真值为准。
- **D 线（跨页）**：把同一检测器应用到 index/cart/my 三个布局不同的页面，**跨页健康假阳 0/12**，可见故障检出 2/5（两个大面积缺图全中、三个小面积全漏，2/2 检出即对）。它证明 0 假阳**跨布局成立**、检测器不是只对首页调参。

### 5.2 A 线分项：分块 SSIM 是关键工程增量

A 线各方法对比（产物 `campaign_20260531_033057`，N=20）：

| 方法 | 检出率 | 健康假阳 |
|---|---|---|
| 整图 SSIM（原通道） | **20%** | 0% |
| 分块 SSIM（本轮新增） | **50%** | 0% |
| ours（多通道） | **50%** | **0%** |
| crash-only | **0%** | 0% |
| RCA top-1 | **40%** | — |
| 条件 RCA | **8/10 = 0.80** | — |

**分析**：分块 SSIM（50%）是整图 SSIM（20%）的 **2.5 倍**。原因是长滚动页里的局部改动会被整图 SSIM **稀释**——一处小改动平均到整页相似度几乎看不出来；切成 8×3 网格后局部敏感度恢复。这是本轮最硬的工程增量，也解释了为何"多通道"检出率与"分块 SSIM 单通道"相同（分块 SSIM 是并集里的主贡献者）。RCA top-1 仅 **40%** 而条件 RCA 达 **0.80**，差距来自**未检出的故障无法分维度**——瓶颈在召回，不在分诊（详见 §5.5 局限）。

### 5.3 D 线稳定性门控：0 假阳不是运气

| 页面 | 干净渲染两两分块 SSIM |
|---|---|
| index | 全 = 1.0 |
| my | 全 = 1.0 |
| cart | 全 = 1.0（低于 0.85 的对数 = 0） |

（产物 `mystab/stability.json` + `cart_stability.json`）

**分析**：三页各自连续干净渲染、两两分块 SSIM 全为 **1.0**，说明三页都是**确定性渲染**——因此 D 线的 **0/12 健康假阳**不是偶然，而是建立在"渲染本身无抖动"的可验证前提上。这也佐证了 §4.5 的协议要求：基线必须同构建。

### 5.4 根因定位结果

| 能力 | 产物文件 | 结果 |
|---|---|---|
| 视觉→源文件（单点 hash，旧） | `localization_v2` | 4/10 = 40% |
| 视觉→源文件（bbox 面积排序，新） | `localization_v2` | **文件级 8/10 = 80%；组件级 9/10 = 90%** |
| 功能 字段→源码行（给定坏字段名） | `field_line` | **5/5 = 100%** exact |
| 功能 page.data 坏字段→源码行（端到端闭环，离线合成数据） | `datafield_loop` | **4/4 = 100%** |

**分析：**

- **视觉定位经三步迭代**：class 映射 **0/10**（被框架 wrapper 类污染）→ data-v hash + 单点 **4/10** → data-v hash + bbox 面积排序 **8/10 文件级 / 9/10 组件级**。每一步都先实跑、读产物、独立重算再下结论。bbox 把 4/10 提到 8/10，是因为单点漏掉的故障元素虽在 tile 中心被相邻/容器元素占据，但其**交叠面积最大**，被面积排序正确选中。剩 2 条 MISS 集中在 `width@category`（真值是 `@import` 的 `.scss`），其中 1 条组件级命中、1 条真错，故文件级 8/10、组件级 9/10。
- **字段→行 5/5**：给定坏字段名，纯静态解析全部命中各自源码行——`XtxGuess item.name→L64 / item.price→L67`、`HotPanel item.title→L15 / item.alt→L16`、`CategoryPanel item.name→L20`。这一步衡量的是确定性的"最后一公里"。
- **page.data 闭环 4/4**：把运行时数据层与字段→行打通，端到端命中 `guessList[0].price→L67`、`name→L64`、`HotPanel alt→L16`、`CategoryPanel name→L20`（由合成 page.data 驱动）。
- **真机已验证通过**（`datafield_live_inject.json`）：minium 连 devtools 实测 youzouzou `/pages/others/others`，`setData` 注入 `list[0].id="undefined"` → 真机字段扫描器抓到 `broken_field_paths=["list[0].id"]`（caught_on_device=true），恢复后干净。即"读真实 page.data → 指名坏字段路径"在真机端到端跑通，平台不对称优势坐实。

### 5.5 负结果（方法学严谨的体现，全部实测）

诚实的负结果与正结果同等重要，它们划定了方法的边界。

- **R1 — H5 零侵入性能维 = 盲区**：向 onLoad 注入阻塞 1.4s，墙钟 time-to-content delta **同一注入两次为 1359ms 与 172ms**（方差大于注入量，不可复现）；headless Long Task API 对 1.4s 阻塞**只报约 80ms**；FCP 不变。结论：H5 零侵入**检测不到主线程阻塞**，性能维是盲区——既然检不出，就无从定位。
- **R2 — 残留假阳的真因是跨构建基线（非轮播抖动）**：同会话/同构建 FPR **0%**；旧 build 的 baseline 与新 build 渲染整体 SSIM 约 **0.49** → 跨构建混用产物**全假阳**。这一发现催生了协议铁律"基线必须同构建"（§4.5），并已修复。
- **R3 — Qwen-VL 单图 = 系统性偏见**：对带网格纹理的占位图，Qwen 对**每一张**（含健康基线）都判 `has_missing_image=True`——表面上 **100% 检出**，实则**健康页 100% 误报**，是"无脑全报警"的假象。差分融合（图+基线+代码）能消除偏见但太保守（recall 降到约 30%）。结论：**Qwen 当前不可用作视觉检测通道**；正确用法是"已定位区域的解释器"，而非"检测器"。这条负结果的方法学教训是：**高 recall 必须与 FPR 一起看**，只报 recall 会得出"Qwen 吊打 ours"的错误结论。

> 性能定位的可行路线（调研结论，尚未打通）：若能先解决检测，CDP Profiler（Playwright `newCDPSession` 可驱动）+ source-map 可给函数+行级确定性定位；但**检测是前提，目前卡在盲区**；原生微信深 CPU profiler 是 GUI-only，minium 拿不到。

## 6. 讨论与思考

### 6.1 创新点：不是简单缝合

相对中期的"概念 + demo + 硬编码"，本项目的真实增量是**结构性的**，而非把现成模块拼接：

1. **从 demo 到真实第三方 app + 源码变异基准 + bootstrap CI**：中期实测仅 3 项、性能 900ms 硬编码、准确率"待补充"；现在 A 线给出 **50% [CI 30–70%] / 0 假阳**这样**可复现、带置信区间**的数字。
2. **从"三重断言概念"到真信号驱动的三轴分诊**：中期 perf 硬编码、layout 未接入决策；现在 C 线接真 `wx.getPerformance`/`page.data`/真几何，layout 已接入。
3. **从规则匹配到源文件/源码行级定位**：视觉 **8/10**、字段→行 **5/5**、page.data 闭环 **4/4**，且确定性、零 LLM。
4. **从单 demo 单截图通道到双路径架构**：H5 + devtools 互补盖盲区 + 跨页 + 每页稳定性门控。
5. **从无评测到一批诚实负结果**：Qwen 偏见、性能盲区、跨构建假阳——证明方法学严谨，而非选择性报喜。

其中，**维度级分诊（triage）+ 确定性源文件/行定位**的组合，是相对纯检测工作（停在 pass/fail 或热力图）的核心差异化：报警即指对子系统、再指对文件，把开发者注意力引导到正确方向。

### 6.2 局限（诚实）

- **样本小、CI 宽**：A 线 N=20，ours 95% CI **[30%, 70%]**——区间宽是小样本的必然。需扩到多 app/更大变异集才能收窄。
- **整体检出受召回限制（约 50–60%），瓶颈在召回不在分诊**：条件 RCA 高（A 线 0.80）但 top-1 仅 40%，因为没检出的无法分维度。系统性漏检集中在**低对比度文字改色**（改动像素占长页比例太小，分块 SSIM 也被稀释）、**无 token 空绑定**（既无明显像素特征也无 `undefined` 字面量）、**主线程阻塞性能**。
- **性能维盲区**（R1）：H5 零侵入抓不到主线程阻塞；devtools 路径 `wx.getPerformance` 的 firstRender 是启动一次性记录、relaunch 不刷新。性能维当前**未达可用**。
- **learned 模型不作主力**：learned 五分类 verdict 对输入特征是否完整不稳定（传/不传 `dom_info` 判定会翻转），仅作可选加权器、不进 headline；检出率以稳定图像通道（分块 SSIM）为准。

### 6.3 平台不对称洞见

一个贯穿全项目的洞见是 **H5 与原生（minium）路径之间的不对称**：

- **功能字段名的运行时恢复**：在 **minium 原生路径上是直接的**——`page.data` 直接以结构化命名列出坏字段（`devtools_probe.collect_data` 已新增 `suspicious_fields`/`broken_field_paths`）；而 **H5 prod 编译掉了 `{{ }}` 表达式、Vue per-node 实例不可达**，字段名的运行时恢复在 H5 路径上**仍是缺口**。
- **性能深剖**：H5 可用 CDP Profiler（若先解决检测）；原生微信深 CPU profiler 是 **GUI-only，minium 拿不到**。

这说明：**没有单一路径能覆盖全部维度**。双路径架构不是冗余，而是对"平台能力不对称"的必要应对——H5 长于大样本与视觉，原生长于结构化数据与字段命名。这一洞见直接决定了未来工作的方向。

## 7. 结论与未来工作

### 7.1 结论

Vision-Triage 在真实第三方小程序上，以**源码变异即真值**的可辩护协议，验证了两个有数据支撑的结论：(1) **常规崩溃测试对非崩溃故障近乎全盲**（A/B 线 crash-only 0%；C 线 42.9% 检出却 50% 健康假阳）；(2) **一旦检出，维度归因高度可靠**（A 线条件 RCA 8/10、B 线 5/6、C 线 3/5），并能进一步确定性定位到源文件（视觉 8/10）与源码行（字段→行 5/5、page.data 闭环 4/4）。系统以 0 健康假阳为约束、带 bootstrap 置信区间报告，并诚实披露三类负结果与平台不对称。

我们**不主张**：100% 检出/RCA、超过所有前人、ML 可跨任意小程序泛化、零侵入即可完整定位性能根因。

### 7.2 未来工作

1. **minium 字段恢复的真机验证**：把 §4.4(c) 的 page.data 闭环（当前离线合成 4/4）在真机上端到端跑通——这是补 H5 功能定位缺口、利用原生路径优势的最直接一步。
2. **性能维 CDP Profiler 打通**：先解决 H5 性能**检测**（Long Task Observer 或 SDK 语义上报），再以 CDP Profiler + source-map 做函数+行级确定性定位，闭合当前性能盲区（R1）。
3. **扩 app / 扩样本以收窄 CI**：增加第三方 app 与变异规模，把 A 线 [30%, 70%] 的宽 CI 收窄，并补 per-dimension 指标与跨 app 通用性证据。
4. **召回攻坚**：针对低对比度文字改色、无 token 空绑定两类系统性漏检，引入更敏感的局部差分与数据层信号（而非依赖大模型，Qwen 偏见已证不可用作检测器）。

## 二、三类诊断的本质依赖（这是项目最核心的认知）

经过这一轮在真实 app 上的反复实证，得到一个清晰且可辩护的结论——
**没有任何单一信号能覆盖三个维度，每个维度有其不可替代的本质信号源：**

### 视觉诊断本质依赖：**与"已知正确基线"的局部化对比**
- 不是"单图判断有没有缺陷"，而是"当前 vs 健康基线，局部哪里变了"。
- 实证：Qwen 单图把带网格纹理的占位图当成"缺图"，对所有图（含健康）100% 报警——**单图缺少"应该长什么样"的参照**。
  给它配上基线图做差分后，它才不再无脑报警（健康判 no-defect）。
- 实证：整图 SSIM 在长滚动页失效（局部改动被全图稀释，召回 20%），**分块 SSIM** 恢复局部敏感度（召回 50%，2.5×）。
- **本质 = 回归对比 + 局部结构**，而非绝对判断。

### 功能诊断本质依赖：**数据层信号（业务预期值 / 可机读异常 token）**
- 像素是最弱的代理：字段绑错渲染成空串时，画面几乎不变（分块 SSIM 也抓不到）。
- OCR token 又有噪声：R3 把 OCR 误读的 `{{` 当未渲染模板 → 健康页假阳（已修，限制为真实 DOM 文本才查）。
- 真正可靠的是读到**数据层**：devtools 的 `page.data`（扫 undefined/NaN）、或业务上报的 visible vs expected。
- **本质 = 数据层对比**，图像只能兜底"有 token 的"那部分。

### 性能诊断本质依赖：**运行时计时探针**
- 截图根本抓不到性能：截图发生在渲染完成后，画面已稳定（实测 onShow 阻塞 1.4s，纯截图/零侵入计时全漏）。
- 必须有"时间维度的运行时信号"：`wx.getPerformance()` / Long Task Observer / SDK 的 markInteractionStart-End / 内存告警计数。
- **本质 = 运行时计时**，图像和静态 DOM 都不够。

> 一句话：**视觉←图像基线对比，功能←数据层，性能←运行时计时。** 三者正交，这正是"多通道融合"不是缝合、而是必要的根本原因。

## 三、项目解决了什么问题

**小程序 / uni-app 中大量存在的"非崩溃故障"——视觉错乱、布局溢出、数据绑定错、性能卡顿——常规自动化测试天然漏掉。**

实证：在真实第三方 app 上注入这类故障，**崩溃测试检出率 = 0%**（A 线 20 变异 / B 线手挑，crash-only 全 0；devtools 线 crash-only 虽 43% 但健康页假阳 50%）。
这类故障不抛异常、不崩溃，lint 和崩溃门禁完全看不见，但用户能直接看到。

Vision-Triage 不只回答"页面坏没坏"，而是**分诊（triage）到可行动维度**：坏在渲染/布局、数据绑定、还是性能——
把开发者的定位成本从"全页排查"降到"按维度排查"。

## 四、相比"简单缝合"的创新

"简单缝合"= 把 SSIM + 规则 + OCR + 大模型堆在一起报个总警。本项目真正能站住的创新（含诚实的负结果）：

1. **维度—本质信号映射 + 分诊路由**（第二节）：不是笼统报警，而是明确每个失效维度的不可替代信号源，按维度路由。
   这把 detection（坏没坏）升级为 triage（坏在哪一维），与 Owl Eyes/Trident（detect/describe）正交、与 Uber（service 级 RCA）正交。
   **实证支撑**：三条证据线"检出即维度判对"= A 8/10、B 6/6、C 4/4。

2. **分块 SSIM**：发现并定位了"整图 SSIM 在内容密集长页失效"这一具体工程问题，分块化召回翻倍。

3. **零侵入能力边界的实证刻画**：用真实 app + 混合池 + CI 诚实地证明"纯截图能覆盖视觉、覆盖不了性能/无 token 数据；
   devtools 补数据与几何；性能必须运行时探针"。**这种能力边界的实证本身是贡献**——它告诉后来者每条路的天花板在哪。

4. **三个有价值的负结果**（避免别人踩坑）：
   - Qwen 单图对占位纹理图有**系统性偏见**（全判缺图），**必须图+基线成对差分**才消除——验证了"代码/基线要和图一起喂大模型"的设计直觉。
   - learned 五分类 verdict **对输入完整性不稳定**（传不传 dom 会翻转 Pass↔RenderBug）→ 应降权为辅助，不作主通道。
   - "0 健康假阳"曾是假象——只在"基线与被测同帧"时成立；混入真正的正确样本立刻暴露 R2/R3 两个假阳 bug + 渲染非确定性风险。

5. **评测方法学**：真实第三方 app + 源码变异（变异即真值，Just et al.）+ 配对健康对照 + 混合池 + bootstrap CI，
   而非"在自建 app 上打自己造的 bug 报点估计"。

## 五、对真实开发测试的帮助

**落地形态 = 跨端小程序的 CI 视觉根因门禁（zero-touch visual root-cause gate）：**

```
PR 提交 → 自动编译(H5/小程序) → headless 截图 + 读 DOM/page.data + 运行时计时
        → 与基线分块比对 + 维度分诊
        → 报告："首页 渲染维度 回归（猜你喜欢区块图片缺失）" / "数据维度（价格渲染 NaN）" / "性能维度（首屏 +1.4s）"
```

- **填补真实空白**：常规 CI 的 lint + 崩溃门禁对非崩溃 UI/数据/性能故障**零覆盖**。
- **可行动**：不是"截图变了"，而是"坏在哪一维"——直接派单给对应方向。
- **成本可控**：规则/SSIM/几何/数据 token 优先，大模型只在歧义带可选升级。
- **零/低侵入**：纯截图 + devtools 只读，不改被测应用一行代码、不影响其功能。

**诚实的部署前提（不藏）**：
- 整体检出受召回限制（稳定图像通道约 50%，漏"小面积低对比度文字/无 token 空绑定/主线程阻塞"三类）。
- 性能维需接 Long Task / SDK 才可用，当前纯截图路径是盲区。
- 基线须与样本**同一次构建/渲染**（R2 实测订正：残留假阳真因是跨构建产物整体差~0.49，非轮播抖动；同构建 FPR 0%）；真实 CI 的非确定内容（轮播/随机/时间戳）用 `calibrate_dynamic_tiles` 标定跳过动态区（单元已验证，本确定性 fixture 不演示）。
- 样本量仍小（单/双 app，N=20/7），结论是带 CI 的点估计，需扩到 3 app/60+ 变异收窄区间。
